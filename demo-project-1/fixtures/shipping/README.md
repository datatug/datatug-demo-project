# Synthetic shipping investigation fixture

This is an unpublished training artifact, not a public endpoint or execution grant. `shipping-working-copy` is a reserved source identity requiring backend admission for an owned isolated workspace. Project cloning alone grants no source writes. Existing Northwind and the independent 11039 log example remain unchanged.

Run `python3 scripts/build-shipping-fixture.py` from the repository root. The generator recreates only this fixture's generated files; `--output /temporary/directory` builds a disposable copy. Run `python3 -m unittest discover -s tests -p test_shipping_fixture.py` for deterministic rebuilding, SQL evidence, negative controls, recovery, and byte-range checks.

`base.sqlite` contains application records, not imported log entries. Its manifest pins schema/database bytes and independent immutable base and per-request recovery direct-file log artifacts. Log byte ranges are half-open `[byte_start, byte_end)`, include the terminating newline and are verified against the whole artifact SHA256 and entry SHA256. Reads must remain bounded; incomplete/failed parsing is unavailable evidence. Preserve all immutable artifacts and historical query/check receipts. Each per-request recovery artifact describes deterministic replay events; admit that request’s recovery artifact only when its governed replay commits those events. This keeps a pending 11062 replay out of 11045 recovery evidence. Never expose future recovery rows as current observations.

All event times use the declared synthetic UTC clock at one-second precision. The business clock starts at 2018-05-20T10:00:00Z; runtime evaluation wall time is separately recorded by the Check engine. Correction 18 takes effect at 10:05. Base 11045 ends at routing blocked, with no partner-call span. 11038 is a healthy synthetic accepted attempt. 11062 is separately pending replay. IDs 90001–90005 are controls for missing/ambiguous/disabled routes, wrong-message receipt and publication-only acknowledgement.

The saved queries use actual `QueryDef` JSON: SQL text lives in the paired `.query.sql`, `connectionId` names the separately admitted source, and `order_id` is a required integer. The Check files use Core `detective.Check`, input bindings and set `row-count` validators. Receipt requires an exact receiving-side request/message match. Assignment uses three separately explainable query steps. Source failure must block, never pass.

Historical diagnosis joins shipper plus attempt configuration revision then partner identity; unmatched requests remain. Current readiness evaluates the workspace's current effective configuration. Correction alone leaves assignment missing; replay commits a new attempt and accepted assignment with a stable unique deduplication key. `correct`/`replay` Python functions are test helpers, not a hosted authority boundary. Backend must enforce project owner, source rights, expected workspace generation, and explicit mutation authorization before executing equivalent operations. Checks remain read-only. Generation is unchanged through correction/replay. Reset creates a new generation; archive old immutable artifacts/history under their original source identity so old evidence remains readable but cannot authorize closure in the new generation.

`events`, `timings` and `readiness` provide real milestone, paired endpoint duration and route/assignment heatmap fields. Renderer/board variants are intentionally deferred to the owning shared chart contract. Company data stays a separately executed Northwind query; these definitions do not claim cross-engine SQL federation. Hosting, catalog admission, isolated working-copy provisioning, log mounting and source binding remain provider/backend responsibilities.


## Evidence-chart held-result contract

The timeline maps `attempt_id` → lane, `kind` → event, `sequence` → sequence, `occurred_at` → observed time, `clock_domain` → clock domain, `precision_ms` → precision, `status` → status, and `evidence_ref` → typed evidence. `readiness` is already long-form: `request_id` → row, `expectation` → column, `status` → status and `evidence_ref` → evidence. Status values are exactly pass/fail/unknown; there is one cell per request/expectation. No client row transforms are required. `timings` retains each endpoint's event ID, immutable artifact digest and byte range.

Raw SQLite cannot mint a hosted query execution identity. Therefore evidence-ref columns are NULL until the governed source/result adapter attaches the **actual** `apicontract.Result.Execution` as Core `ArtifactRef{kind: execution, execution: {storeId, projectId, executionId}}` to the held result. This adapter must persist the same execution snapshot and retain physical source generation/collection/key and log provenance columns. It must preserve the original raw fingerprint/source provenance and attach presentation metadata without recomputing business rows. Selection must retain exact `row_key` and open the same execution and held row, not an unfiltered whole query or hidden rerun. It must not invent IDs, use a query-definition ref as execution evidence, or fill missing refs with a public URL. Raw rows with NULL refs are unavailable for admitted evidence-chart drill-down; field-schema/query compatibility is not proof of hosted chart readiness. The provider integration remains required.

Accepted assignment must match the latest attempt **and** current configuration, the unique current effective route and its enabled partner. A later configuration invalidates the old green assignment, while historical config17 failure evidence remains intact.

`manifest.json.chartAdmission` records the exact column mappings and unresolved provider integration gate. The Go integration test feeds raw NULL slots through actual Core `ArtifactRef.Validate`, proving that these raw rows are refused as admitted evidence. That test does not prove the future provider enrichment or renderer journey; those need real persisted execution/snapshot/selection acceptance.
