# Watch the existing order 11045 investigation

The Watch demonstration reuses `shipping-carrier-assignment`, its saved queries,
validators and the existing synthetic Shipping fixture. It observes carrier
assignment, rather than asserting that the physical order has shipped.

Run the native acceptance with a DataTug executable that includes Watch:

```sh
python3 scripts/watch-shipping-integration.py --datatug /path/to/datatug --local-owner-fixture
```

The script creates a new private runtime directory, starts one combined
coordinator/runner and two outbound runners, and gives Alice, Bob and Carol
independent personal Watches and subscriptions. Their user tokens and the runner
tokens are random environment values. Credentials do not enter the project
manifest or the acceptance receipts.

`--local-owner-fixture` explicitly opts the **private synthetic copies** into local
owner mode. Their unrelated Customer/Invoice policy documents are preserved under
`.watch-demo/archived-policies`; an ownership/provenance marker records the setup.
The source project's policies, SQLite fixture and direct log files stay unchanged.
This setup does not demonstrate secured project-asset grants. Source execution
uses the existing read-only Check executor against the copied application SQLite
file; it does not import logs into another database.

The executed journey checks these outcomes:

1. Three native runner processes register and the existing Check observes the
   missing assignment.
2. The existing correction helper alone leaves the Check false on a new accepted
   evaluation. Replaying the existing recovery artifact makes it true.
3. Alice's one-shot Watch completes once. Bob's and Carol's continuous Watches
   record failure, recovery, and a deliberate later failure. Unchanged results do
   not create repeat notifications.
4. All seven expected email messages reach a private file sink. In-app inbox,
   personal visibility, delivery history and definitions survive a coordinator
   restart. No external email recipient is contacted.

To include the actual browser journey, first build the DataTug Apps production
artifact and install its Playwright Chromium dependencies, then add
`--ui-worktree /path/to/datatug-apps` to the command. This starts the real project
agent, consumes its normal one-time connection link, and uses the actual
coordinator API for Check → create Watch → channel consent → details/status/history
→ inbox → cold details. It captures desktop and narrow screenshots. Browser traces
are disabled for this lane so bearer credentials are not retained in trace files.
The existing analytics rejection control is used normally before screenshots.

`receipt.json` contains phase observations/run IDs, definitions, delivery outcomes,
the executable hash and private sink filenames. `native-receipt.json` preserves
native phase evidence even if a later browser assertion fails. `cleanup.json`
records the owned child PIDs and their exit status. A `finally` block stops only
those child processes; no launchd job is installed. Keep the runtime artifacts
private and remove their directory after inspection.

This native/browser procedure was executed locally against the combined Watch
candidate on 2026-10-23. Release CI and deployment acceptance are separate gates.
